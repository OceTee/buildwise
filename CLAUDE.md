# BuildWise

An AI building assistant plus a construction marketplace. The front page asks "What would you like to build today?": the user picks a building type (homes up to 10-storey flats, commercial, hospitality, institutional), gives the plot and a few choices, and BuildWise designs it: a concept checked against building rules, in 3D at true scale, with drawings, systems, costs, a bill of materials and where to buy each line from live marketplace listings. Shoppers go straight to `/market`. This repo is **Releases 1, 2 and 3** (R3 in four slices: structured procurement, fulfilment, trust and marketplace quality, then tenders, contracts and sourcing) of the spec in `docs/spec/construction-platform-full-build-technical-specification-v3.md` (R1 = marketplace website, §3; R2 = private project workspace with documents, takeoff, RFIs and reviewed estimates, §7–§12, §14.1; R3 slice 1 = RFQs, quotes, comparison, award and record-only orders, §9.2–§9.4, §10.4 steps 1–7, §13.1; R3 slice 2 = deliveries, POD, inspection, discrepancies, returns, three-way match, §9.4, §10.4 steps 7–9; R3 slice 3 = supplier cases, transaction reviews, provider performance, liquidity dashboard, §9.10, §13.3, §13.4, §25; R3 slice 4 = sealed tenders, milestones, variations, sourcing modes, client supplier lists, supplier uploads, §9.5, §9.6, §10.4 step 2, §10.5, §13.1.5, §19.2; roadmap in §25). Nigeria is the worked example; the bundled market pack `demo-2026.1` is illustrative and its values are *proposed*.

`README.md` is detailed and accurate: read it for feature tables, seeded demo accounts and provider setup.

## Layout and module boundaries

pnpm workspace (`apps/*`, `packages/*`), ESM everywhere, TypeScript 5.9, Node 22+ (this machine: Node 24), pnpm 10.34.9.

| Package | What it is |
|---|---|
| `packages/domain` (`@bw/domain`) | Pure TypeScript rules, no I/O. Exports `src/index.ts` directly (no build step; web transpiles it via `transpilePackages`). Units and per-unit price comparison, market pack, listing/promotion/quote/estimate state machines (`defineMachine` in `core.ts`), content checks, trust, takeoff, estimates, design engine, assistant model. |
| `apps/api` (`@bw/api`) | Fastify 5 API run with `tsx` (no compile step). Postgres via `pg`, or embedded PGlite when `DATABASE_URL` is unset. |
| `apps/web` (`@bw/web`) | Next.js 16 App Router, React 19, three.js via `@react-three/fiber` + `drei`. `output: 'standalone'`. |

`pnpm check:boundaries` (`scripts/check-module-boundaries.mjs`, regex over imports) enforces:
- `packages/domain/src` imports no fastify, pg, PGlite, `node:fs`, next, react, sharp or `apps/`.
- `apps/web` never imports `apps/api` / `@bw/api` / pg / PGlite / fastify: it reaches the API over HTTP only.
- `apps/api/src/platform` and `apps/api/src/http` never import `modules/`; `apps/api/src/db` imports neither `modules/` nor `http/`.

## API (`apps/api/src`)

- `app.ts` `buildApp(overrides)`: loads config, opens the database, runs migrations, builds `Services` (`config, db, pack, storage, sms, email, payments, limiter`), syncs categories from the market pack, registers every module. `/health` reports driver, providers and env. `/v1/internal/cron` (Bearer `CRON_SECRET`) runs one worker cycle.
- `server.ts` (dev/start, port 4000, runs the worker in-process unless `RUN_WORKER_IN_PROCESS=false`), `worker-main.ts` (stand-alone worker), `vercel.ts` (serverless handler, one Fastify per warm instance), `seed.ts` (demo data through the real API; skips if users exist).
- `config.ts`: env is `development | test | staging | production` (`APP_ENV=staging` selects staging; an unknown `NODE_ENV` gets production checks). Deployed envs refuse dev secrets, missing `DATABASE_URL`, `OTP_LIMIT_PER_HOUR`, and a non-postgres rate-limit store; production also needs a real SMS provider and a live Paystack key.
- `http/route.ts` `route(app, s, def)`: every endpoint goes through it. It does per-IP rate limiting, JWT (HS256, `jose`) session auth checked against the `sessions` table, zod validation of body/query/params, idempotency keys, and runs the handler inside **one DB transaction per request**. Signed-in requests `set local role app_user` + `app.user_id` so Postgres **row-level security** is a second layer; `systemContext: true` runs without RLS (staff cross-project routes and the public assistant). Client IP/device id are trusted only with the `x-internal-secret` header from the web server. Errors use `ApiError` → `{ error: { code, message, fieldErrors?, correlationId } }`. Money is bigint, serialized as strings.
- `db/`: `database.ts` (PGlite transactions are serialized; pg pool max 3 on Vercel), SQL migrations `001_init` … `018_notifications` (016 is `016_rls_marketplace`, which puts RLS on every table; 017 is `017_data_rights`), and `migrations.generated.ts` (embedded copy for bundled deploys; regenerate with `node scripts/embed-migrations.mjs` after any migration change — a test fails if stale). Migrations run on every API start.
- `platform/`: `platform.ts` (errors, audit hash chain, outbox `publish`, notifications, local/Vercel Blob storage, signed file tokens, content sniffing, dev malware scanner that only knows EICAR, sharp photo pipeline with dHash, file/log message channels, webhook signing); `providers.ts` (Twilio/Termii SMS, Resend email, dev/Paystack payments, memory/Postgres rate limiters; all take an injectable `fetch` for tests).
- `modules/`: `identity` (phone OTP, sessions, businesses, correction), `privacy` (export, deletion), `staff` (TOTP, staff roles), `listings` (categories, listings, search incl. `searchListings`), `contact` (chat, phone reveal, quote requests, reviews, favourites, saved searches), `moderation` (risk-ordered queue, reasons, reports, restrictions, two-moderator rules, appeals, verification), `promotions` (hosted checkout, signed webhook is the only thing that marks paid, invoices), `effects` (shared side effects of listing status changes, incl. pausing/crediting/forfeiting promotions), `projects`, `documents` (upload, scan, revisions, takeoff), `estimates` (indicative / client / reviewed estimates, QA, issue as hashed snapshot, rates), `procurement`, `fulfilment`, `cases`, `transaction-reviews`, `reputation` and `liquidity` (R3, below), `build` + `assistant` (below).
- `worker.ts`: idempotent cycle: dispatch outbox events (mirrored to SMS/email), time-based transitions (expiry, promotions), saved-search alerts, document processing, assistant retraining.
- Timeliness (public beta, §16/§21.1; migration `018_notifications`; `sms_usage` is server-only, every SMS is sent in system context, project invitations via the `ProjectInvitationSent` event): `publish()` records each event id in an AsyncLocalStorage collector (`platform/background.ts`), and `route()` hands a committed request's ids to `services.afterCommit`, which dispatches them in the background (`inBackground`: `waitUntil` on Vercel, in-process elsewhere; `DISPATCH_AFTER_COMMIT=false` turns it off). Dispatch claims rows (`update outbox set claimed_at … where event_id in (… for update skip locked)`, a 5-minute lease), so inline dispatch, the worker and the cron never send an event twice; an event whose only copies failed is released for retry. Without an in-process worker (Vercel), ordinary requests run `runTimedWork` (documents, expiries, saved searches, outbox) at most every `CATCH_UP_SECONDS` (default 60) per instance; `runExpiries` takes `pg_try_advisory_xact_lock(727275)`, listings are claimed `for update skip locked`; the daily cron stays as the safety net. Time-based state is right when read: public listing queries add `expires_at > now()`, `requireOwnListing` / `GET /v1/my/listings` expire due listings there and then (`settleListing(s)` in `effects.ts`), `rfqRow()` closes a passed RFQ deadline (`closeAtDeadline`, notifies both sides) and expires quotes past validity (`expireQuotes`) as far as RLS lets the reader, and views use `rfqStateAt` / `quoteStateAt` / `listingStatusAt` (`packages/domain/src/notifications.ts`). Promotion slots already filter on `ends_at > now()`.
- Notifications: `notifyCoalesced()` keeps one unread notification per `(user, group_key)` (chat `thread:<id>`, quote requests `quotes:<id>`) through the security-definer `app_notify_coalesced` (RLS stops app_user updating another person's row); opening a thread reads them. `MessageSent` is copied off-platform only for the first unread message (`mirrorTo`), never with the message text. Copies follow `users.notification_prefs` per topic (`messages`, `quotes`, `listings`; defaults email on, SMS off for chat): `GET/PUT /v1/me/notification-preferences` (`modules/notifications.ts`), control on `/account`.
- SMS caps: every SMS goes through `platform/sms.ts` (`sendSms` / `reserveSms`): a conditional upsert into `sms_usage (day, scope)` against `MarketPack.messaging` (`smsDailyCap`, `smsDailyCapByCallingCode`, `smsWarnAtPct`; day in the pack's time zone). Past a cap the OTP request answers 503 `SMS_UNAVAILABLE` ("try again later") and the refusal is recorded in its own transaction; the first warning and first refusal per scope and day notify ops admins (`kind: 'ops'`), write an audit event and publish `SmsCapReached`. The OTP limit checks take `pg_advisory_xact_lock` on the number, IP and device (in that order) before counting.

## The build assistant, end to end

1. `/` → `WelcomePrompt` (building-type links `/build?type=…`, or a sentence `/build?q=…`) → `components/build/BuildWizard.tsx`. Three create steps (`CreateSteps.tsx`: **what** type cards, **where** plot + town, **make it yours** storeys / units / bedrooms / extras / style / budget), then **"Design it for me"**: `designForMe()` shows the work as it happens (`GeneratingPanel`), waits for the AI designer (skippable, 10 min cap: a Claude design takes ~7 min), the 3D critique (7 min cap) and the AI architect (120 s cap), records the layout as a *proposed* decision and lands on **your design**: a photo-mode 3D hero plus `ConceptCard` (name, story, moves, palette, stats, download image, photoreal render, drawings) and tabs: overview (notes, checks, floors, other directions, house plans), adjust rooms, outdoors, systems, cost, materials, where to buy, record. State in `localStorage` `bw-build-v1` (old step names are mapped).
2. `GET /v1/build/config` returns the market pack's `design` rules and currency so the browser designs with the same values.
3. `POST /v1/build/interpret` (public, system context, rate-limited by `ASSISTANT_PER_MINUTE`): `getBrain()` (cached 5 min per instance) + `respond()` from `@bw/domain` `assistant.ts` returns intent, plot, brief patch and a templated reply. The message is stored redacted (`redact()`) in `assistant_messages` against an anonymous session hash (`sessionOf`). Without a live brain no external AI service is called.
   - Model: naive Bayes intent classifier over words and bigrams with uniform priors (seed data in `assistant-seed.ts`: about 440 examples incl. Nigerian English and Pidgin, a held-out `SEED_TESTS` set at ≥ 95%, about 70 knowledge answers), rule-based brief reading plus a learned phrase lexicon, BM25 over a knowledge base (seed, staff, platform price facts), scope check using building vocabulary, and a short-greeting rule. `build_home` means any building BuildWise designs (all 13 types); `other_project` is work it does not design (repairs, renovations, fences, boreholes, finishing).
   - Live brain (optional, `ASSISTANT_PROVIDER=gemini`): the route is registered with `app.post` (no DB transaction during the model call). The local model always answers first and stores the message; then `services.brain.read()` (`createGeminiBrain` in `platform/gemini.ts`, prompt `ai/brain-prompt.ts` `brain.v1`, JSON checked against `BrainOutput`) gets the redacted message, the state and the local reading. Its reply is shown (`source: 'ai'`) unless both agree and the local one is a curated knowledge/price answer; its intent and the brief fields it read differently are stored as `teacher_intent` / `teacher_changes` (migration 010). `trainAssistant` uses them: teacher labels (weight 1) where no outcome or staff label exists, teacher changes as phrase signals (same ≥ 3 sessions rule). Daily ceiling `ASSISTANT_DAILY_LIMIT` via `ai_usage` kind `brain`.
4. `POST /v1/build/feedback`: outcome (proceeded/shopped/abandoned), hand changes to the brief, thumbs up/down. Only the same session, within a day, once.
5. Design: `generateDesigns(plot, brief, cfg)` in `packages/domain/src/design.ts` runs **in the browser** (and on the server for the AI architect): up to `MAX_DESIGNS` (4) layouts.
   - Building types: `packages/domain/src/building.ts` (`BUILDING_TYPES`: bungalow, duplex 2–3, terrace, apartments 2–10, shops 1–4, office 1–10, mixed-use 2–10, warehouse, hotel 2–10, event-hall, school, clinic, worship; each with storey range, the `units` it counts, `features`, storey height, corridor, band depths, cost factor, m² per person; `needsLift`, `needsTwoStairs`, `suggestedParking`). `DesignBrief` has `type`, `storeys` (1–10), `units`, `features`; old briefs normalise (2 storeys → duplex). Houses keep the room-by-room `programme()`; every other type gets `programmeFor()` (floors of front/rear bands with a stair+lift core at the start of the rear band and an escape stair at its end from 5 storeys) laid out by the same `layout()` (typology `core`, or `row` for corridor-less terraces) over `typeVariants()` (incl. a single-loaded "Narrow plan"). Too big for the plot → it drops extras, then units, then parking, and says so in `notes`. `reviewBuilding()` writes the notes for non-houses; `describeBuilding()` the summary; `conceptFor()` the engine's concept (the AI's replaces it via `applyAiReview`). A design is one or more **blocks** (`Design.blocks`: house wings plus an optional `outbuilding`, the boys' quarters); every `Room` has a `block`. Houses are planned without corridors (`typology: 'hub'`): `hubPlan()` (`HUB_VARIANTS`: central, generous and compact) lays a house on a 3 × 3 grid. Front row: living room / entrance hall (bungalow: guest WC in its front corner away from food) / dining. Middle row: a stack of rooms each side (`layBand` along y; a suite instead when `mlSuite`) and in the centre a square bedroom lobby (one storey) or the stair with a 1.2 m hall each side (a lift beside it when asked for); halls stop at the stair, and a deeper row gets a cross landing (`Back hall`/`Back landing`). Back row: two suites (`suite()`: the room on the inner side, ensuite + wardrobe in a 1.5–1.8 m strip on the outer wall) whose doors open off the end of the lobby. Duplexes: guest WC at the start of the middle-left stack off the stair hall, guest suite downstairs, noisy rooms on the ground floor behind the kitchen; upstairs a family lounge over the hall, the master suite on the quiet side, every bedroom ensuite. Up to three bedrooms upstairs use two rows (`twoRows`). Form (`HubVariant.project` / `wing`): the living-room column projects forward as a `Living wing` block with the entrance recessed beside it in the `House` block, and the back row is a `Bedroom wing` block that may run past the side of the house into the garden; each block gets its own roof (front wings run into the back wing's roof). `Living pavilion` (storeyed houses) makes the living room a single-storey `Living pavilion` block stepping 2.4 m forward of the two-storey house, with nothing over it upstairs; it is offered only with four or more bedrooms upstairs (fewer would leave filler rooms). `wingBoth` runs the back wing past both side walls (a T, 1.2 m each side) to break long side elevations. The back row's depth comes from each suite's own width (wing extension included), and a wing runs out only as far as its rooms can use (up to 1.6× their target area), at least 1.2 m. A spare upstairs middle cell in front of the master becomes a `Master's lounge`, not a second study. Upstairs, the room over a projecting living wing starts on the house's front line, and the projection becomes a `Loggia`: `loggias(blocks, rooms)` finds any upper-floor part of a house block no room covers (one clean rectangle ≥ 0.9 m), `defaultArchitecture` rails it as a `balcony` element inside the block (the block's slab is its floor, its roof covers it), `architecturePlan` gives the habitable room behind it full-height glass and no separate balcony, and `designFromLayout` counts a balcony inside a block as covered. `solidsFor` stands a column at each loggia corner where two open edges meet and, on flat or hidden roofs, runs the parapet along its open edges. `hubPlan` and `narrowPlan` plan inside `cmInside(envelope)` (whole centimetres) so the Studio's 1 cm snap never pushes a mirrored plan over the setback. `defaultFinishes` clads a house's living wing or pavilion differently (stone for modern and classic, sand render for tropical), and `defaultArchitecture` adds a `Garden terrace` (veranda or pergola) off the widest ground-floor back room when the main outdoor room is not on the garden side, drops outdoor rooms clipped under 1.5 m, and groups the small high windows of bathrooms, WCs, stores and wardrobes on side walls behind full-height `Louvre screen` elements in the accent material (a screen covers at most 4.8 m of windows, so it reads as a panel, not a band). `Compact hall` stays one block. Rooms are assigned to the block that contains them. A store buffers a stack whose first room would clash with the room in front; stores move from the kitchen-side stack to the other only while that makes the middle row shallower, and a middle row past its limit (a bungalow lobby over `maxHouseHallM`, or beside the stair over `maxHousePassageM`, which would add a back landing) first lets its secondary rooms (stores, laundry, study, lounges, leisure) drop to their minimum size, then the kitchen (storeyed) or every stack room (bungalow). An open-plan bungalow puts a bedroom in the front-right cell (bathroom behind it, stores behind the kitchen); a two-row duplex without a guest suite gets a study in the middle-left cell. `narrowPlan` keeps the ground-floor dining room full width (the middle zone is lit only from the side wall) and caps the upstairs family lounge at 1.8× its target with a laundry beside the landing. Its front row's depth is rounded up to the centimetre (rounding down once threw away every 3- and 5-bedroom plan on 12 m plots); upstairs, a front wide enough for both takes a back bedroom beside the master (the master stays next to its ensuite), and spare length at the back becomes a study, not a second lounge. `layBand` gives spare length to a shallow bedroom first, up to 1.6 : 1 (`BEDROOM_RATIO`); `hubPlan` deepens the middle row for that when the plot depth, the hall limit and the coverage limit allow, and `reviewDesign` names (and marks down) any bedroom still longer than 1.75 : 1. `narrowPlan()` covers narrow plots (two or more storeys) in three zones front to back with the circulation down one side. `checkDesign` fails a home whose hall is a strip: passages under 1.6 m wide at most `maxHousePassageM` (4.5), wider lobbies `maxHouseHallM` (7). The older corridor typologies (`hallway`, `l-plan`, `pavilion`) are still generated but now fail that rule for houses. `openingsFor` ends with `connect()`, a door-graph walk from the entrances that gives any unreachable room or hall an opening to a reachable neighbour (each door's two rooms and the hall/stair links are worked out once, so the walk is cheap: the adjust step previews every wall move with it), and long halls get windows. Research behind these rules: `reports/Modern house design for BuildWise.md` (notes in `research_notes/`). Older typologies: `hallway` (5 variants of room bands around a hallway), `l-plan` (bungalows: living wing in front, bedroom wing behind) and `pavilion` (2–3 storey houses, `PAV_VARIANTS`: a compact main house with the entrance hall and the kitchen pinned to the end of their bands (`Item.pinEnd`), beside a single-storey living pavilion that starts at the hallway line, so it steps back to make an entrance court; hallway → dining, kitchen → dining door, living opens off dining; the guest WC sits behind the entrance hall off a `Lobby` with a window to the court, the ground store becomes the kitchen's pantry, spare length a home office). `layBand` caps a kitchen at 1.4× its target and gives leftover length to a living room or bedroom, never a kitchen, store or toilet; fillers never take the master suite's corner. A home guest WC or shared bathroom (`Item.lobby`, sizes in `WET_ROOM`) in a deep band sits on the outside wall (its window) behind a `WC lobby` / `Bath lobby` off the hallway; a store keeps 1.8 m by the hallway and the rest becomes a `Pantry` (beside a kitchen) or `Wardrobe` (beside a bedroom) that opens from that room; a wide master gets a `Walk-in wardrobe` beside a 2.2–2.4 m ensuite. Halls only count for a door when they share ≥ 1 m of wall. Mirrored plans round their start inwards (no 2 mm setback breach); `wallsFor` draws no wall between two halls, so lobbies and galleries stay open to the hallway. `arrange(items, startNeighbour)` also scores the room beyond the band's start (an L-plan wing opening off the living room). In photo mode `Scene` stands the camera on the side of a lower wing (`Bounds.side`). `tryAll` puts the best of each typology in the top 4 before the next best; `candidateDesigns()` returns every passing design (the gallery). A lower block against a taller one gets no eave on that side (`roofParts`). Shared pipeline `finish()`: outbuilding, parking, `wallsFor` (a wall is external when one side has no room), `openingsFor` (doors from a hallway, else a living "hub", else from outside; windows on outside pieces, a second window for cross-ventilation), `checkDesign`, then `reviewDesign` (the engine's own architect's notes and a score; designs are ranked by it). `solidsFor` / `roofPlanes` (one roof per block, exactly 4 planes each; the wing whose ridge runs into a join extends into the other roof) feed `components/build/Scene.tsx` (1 scene unit = 1 m; plan x along the frontage, y into the plot). Bump `DESIGN_ENGINE_VERSION` when output changes (it keys the AI review cache). Always labelled as concept designs.
   - Editor: `packages/domain/src/design-edit.ts`. `DesignEdit` ops (`move` a room side, `split`, `merge`, `rename`, `use`) are replayed by `applyEdits(base, edits)` and the design rebuilt by `rebuildDesign()` (same `assemble()` as the generator). Edits are refused with a reason when they would break minimum room sizes, the building line, the parking in front, wing joins or the stair. The browser keeps them per `designKey(plot, brief, designId)` (roof and style excluded) in `bw-build-v1`. UI: `components/build/EditStep.tsx`.
   - Roofs: `RoofKind` (8 forms), `RoofFinish`, `RoofColour`, `roofPitch` in the brief. `roofParts()` returns each block's planes (built in a local ridge frame in `blockRoof`); upright faces are told apart by `isVerticalPlane`. The bill of materials measures the actual slopes (`planeArea`) and counts gable and infill faces as blockwork.
   - Landscaping: `packages/domain/src/landscape.ts` (`planLandscape`, `landscapeMaterials` with section `external`, `lawnArea`); every item is a rectangle in plan metres. UI: `components/build/OutdoorStep.tsx`; 3D in `Scene.tsx` (`Grounds`); site plan in `DrawingSet.tsx`. Market category `landscaping` for sourcing.
   - Engine gallery: `/build/gallery` (`components/build/Gallery.tsx`) shows every `candidateDesigns()` result for a brief side by side: SVG plans coloured by zone, the planning score and conflicts, any one in 3D. Offline, default rules; for judging the engine.
   - Concept drawings: `/build/drawings` (`components/build/DrawingsView.tsx` + `DrawingSet.tsx`) draws A3 SVG sheets from the same geometry: first the presentation floor plans (`plan-board.tsx` `PlanBoards`, sheets A-001…: levels two to a sheet side by side at one brochure scale such as 1:80, warm grey floors, dark solid walls, rugs under seating, beds and dining sets (`rugsFor`), detailed furniture (`plan-symbols.tsx` `FurnitureSymbol`, each symbol drawn in its own frame and turned to its `back`; the technical plans use the same symbols in line), tiled wet rooms, paved terraces with outdoor furniture, the front door marked, names with `W X Dm` sizes placed clear of furniture and door swings, and `TOTAL AREA: … SQM (… SQFT)`), then A-100 site plan, A-10x floor plans (walls, door swings, windows, furniture, dimension chains), A-201 elevations (painter's order, roof planes projected), A-301 section. It reads the saved build from `localStorage` (`bw-build-v1`); print CSS gives A3 landscape PDFs.
   - AI architect (optional): `POST /v1/build/architect` (body `{ plot, brief, location? }`) regenerates the designs server-side, sends `designDigest()` (numbers only; tall buildings show ground and first floor plus room counts) to the provider in `platform/providers.ts` (`createClaudeArchitect`: `@anthropic-ai/sdk`, `claude-opus-5-5` by default, structured output via `betaZodOutputFormat`, server-side refusal fallback), returns the ranking, notes and a `concept` for its top pick (title, story, moves, palette), caches the review in `architect_reviews` (migration 006) for 30 days, and limits fresh reviews per IP and per day. It is registered with `app.post`, not `route()`, so the slow model call never holds a DB transaction. The browser merges it with `applyAiReview()`; without `ARCHITECT_PROVIDER` it answers `source: 'engine'` and nothing changes.
   - Architecture beyond rooms: `Design.elements` (`ArchElement`: porch, veranda, balcony, canopy, pergola, screen, feature-wall, planter; plan rectangles per storey), `Design.finishes` (`BlockFinish`: walls/base/accent from `MATERIALS`) and `Room.glazing` (standard/large/full-height, used by `openingsFor`). Engine designs get them from the style in `assemble()` (`architecturePlan` before the openings, `defaultArchitecture` after, clipped to the plot); AI layouts bring their own. The BOM counts them (provisional lines).
   - AI designer (optional, the primary designer when connected): `POST /v1/build/design` (`apps/api/src/modules/ai-design.ts`, `app.post`) asks the designer chain in `platform/designer.ts` (`DESIGNER_PROVIDER=anthropic,gemini`: `createClaudeDesigner` (Claude Opus, streaming, `output_config.format` json_schema via `claudeSchema()`) first, then `createGeminiDesigner`, joined by `chainDesigners`; `createGeminiDesigner`: Google's Interactions API `POST /v1beta/interactions`, `response_format` JSON schema from `aiLayoutSchema()`, answer in the `model_output` step; default model chain `gemini-4-hydrogen,gemini-3.8-flash,gemini-3.6-flash`: a busy or failing model hands over to the next; free tier) to compose blocks and rooms with the prompt in `apps/api/src/ai/designer-prompt.ts` (section 4 of the master prompt + geometry rules; bump `DESIGNER_PROMPT_VERSION`). `packages/domain/src/ai-layout.ts` `designFromLayout()` turns a layout into a full design (`assembleFromRooms`, typology `ai`) and lists problems (outside the buildable area, gaps/overlaps from a 0.1 m raster, missing rooms, failing checks); failing options go back once with the problems; only passing layouts are returned and cached in `ai_designs` (migration 008). `POST /v1/build/critique` (`registerCritique`) sends a JPEG snapshot of the 3D design to a designer that can see (Claude) with `CRITIQUE_INSTRUCTIONS`; an improved layout that passes the checks replaces the first one (the browser does this during *Design it for me*). Tall buildings: the model draws ground + one typical floor, `normaliseLayout` repeats it. The browser keeps the layouts in `bw-build-v1` (`aiLayouts`), shows them before the engine's designs (ids `ai-1`, `ai-2`), and sends the chosen layout to the chat; the drawings page rebuilds from it.
   - Photoreal render (optional): `POST /v1/build/render` (`apps/api/src/modules/render.ts`, registered with `app.post`) takes a PNG data URL of the 3D view (≤4 MiB, PNG magic checked), builds the prompt server-side (`renderPrompt`) and calls `RenderProvider` in `platform/render.ts` (`createOpenAiRender`: OpenAI `/v1/images/edits`, multipart, injectable fetch). ## Choices, concepts and evaluation

- `packages/domain/src/preferences.ts`: who it is for (`Purpose`), how it should feel (`Taste`: simple, modern, tropical, grand, each with an engine style, a starting roof and three named swatches) and what matters most (`Priority`: garden, privacy, host), kept in `ProjectRecord.preferences` apart from the brief. A taste changes the look only (`tasteBrief`); grand is spent on the entry, the living space or hosting (`GrandFocus`), never on area or spend, which need their own evidence (`readPreferences` reads budgets, finish levels and solar budgets separately). `readRevision` reads "smaller X but keep Y"; `routeFor` names the BuildWise tool a message needs. `respond()` returns `preferences`, `revision` and `route` with every reply.
- `packages/domain/src/concepts.ts`: `conceptMetrics` (open ground, garden, covered outdoor rooms, circulation, living area, bedroom privacy, arrival, room relationships, massing form), `massingDistance`/`planDistance` on a 0.5 m raster (a mirror image or a recolour scores 0), `conceptSet` (up to three checked designs whose every pair is `distinctDesigns`, best fit to the person's choices first, each with a measured reason, tag and trade-off, and a note when fewer than three differ), `conceptTitle`/`designConcept` (the one name a design goes by on its concept card, the project record, the design page and the drawings: an AI title, else its form, e.g. "Town House", or "Hotel: deep plan" for other buildings; the engine's `conceptFor` supplies only the story and palette), `shapedBy` (two or three choices and what each did in the chosen design) and `reviseBrief` (shrinks the plot, house or budget, giving up only unprotected things). - `packages/domain/src/solver.ts`: the free-form house solver (Phase 1 of "a new concept every time"). A seed composes a house from zones sized by their own rooms, not from fixed layout families: a public zone (living, dining, kitchen in a row with the entrance hall and a guest WC + cloaks column; on plots under 14 m buildable, or by chance, the dining room and kitchen stack in a `Kitchen wing`), and one or two private zones (a lobby of at most a lobby's length with rooms down one or both sides via `layBand`, the master across its end with ensuite and walk-in in a column beside it). Compositions (`FreeParti`): `behind`, `offset` (an L), `pavilion` (a court and a `Gallery` link block), and on plots 16 m+ buildable `side-wing` and `split-wings` (master wing beside the hall, children's wing behind). Duplexes: a single-storey living wing plus a two-storey block whose ground floor holds dining, kitchen and the guest rooms, the stair heading the lobby on both floors (never alone in its band). Rooms are kept to about 1.8 : 1 along their band (`proportioned`), one filler study per floor. Everything goes through the engine's `finish()` (walls, openings, checks, review) via `ENGINE` (internal exports at the end of `design.ts`); only passing designs are kept. Ids are `free-<seed>-…` and `findDesign(plot, brief, id)` rebuilds any design by id (use it instead of searching `candidateDesigns`). `conceptSet(..., { seed, avoidIds })` mixes the solver's designs in (they lead by +6) and drops anything not `distinctDesigns` from what was shown; the wizard keeps `ideas: { seed, seen }` in `bw-build-v1`, draws a new seed on every *Design it for me* and on **Show me new ideas**. Every kept design is also `wellPlanned` (no toilet beside food, no planning clash scoring ≤ −2 such as a kitchen against a bedroom: the same standard as AI layouts), and a run keeps at most two houses per idea so easy ideas do not crowd out the rest. A floor with a kitchen (a duplex's ground floor) puts dining and kitchen down one side of the lobby, bedrooms and wet rooms down the other, a family room across the end; a bedroom block behind the living row slides along the hall until it is clear of the kitchen and the kitchen wing, which stands at the far end of the row from the hall (`publicZone` returns its `main` row span). Narrow plots (under 13 m buildable): the guest WC heads the lobby instead of a column beside the hall, a bungalow's store joins the kitchen wing, the row deepens until it fits the width, and the bedroom block keeps within the row; a 12 m plot gets two-storey solver concepts (a 3-bed bungalow there still only gets the engine's narrow plan). `conceptSet` tries 200 seeds (about 50–130 ms). Probe pass rates and look at plans before changing it.

## Gotchas

- The root `.env` (git-ignored) holds the local `ANTHROPIC_API_KEY` and `GEMINI_API_KEY`, with `BUILDER_AI_PROVIDER`, `ARCHITECT_PROVIDER`, `ASSISTANT_PROVIDER` and `CRITIQUE_PROVIDER` set to `gemini` and `DESIGNER_PROVIDER=anthropic,gemini`: any API you start from the repo calls Gemini (free tier) and, for designs, Claude (paid). Never print it.
- **`.env.local` is a `vercel env pull` of the deployed project: its `DATABASE_URL` / `POSTGRES_*` / `PG*` point at the real Neon database, and it holds a Blob token.** Nothing in the repo loads `.env.local` (the API loads only `.env`), so local runs and tests use PGlite. Never `source` it or copy it to `.env`; never print it.
- Setting `BLOB_READ_WRITE_TOKEN` (or `BLOB_STORE_ID`) in the environment silently switches storage to Vercel Blob.
- Local dev data lives in `~/.buildwise/dev`, outside the repo, because the Next dev server watches the whole monorepo. Delete it and re-run `pnpm seed` to reset. Use `DATA_DIR=...` to keep experiments separate.
- In development the sign-in code is shown on the page and SMS/email go to `<DATA_DIR>/outbox/*.jsonl`. Setting any `SMS_PROVIDER` hides the code and sends real messages; tests never need provider keys.
- e2e against your own running servers needs the API started with `OTP_LIMIT_PER_HOUR=1000`, or let Playwright start them.
- Migrations are embedded: edit the `.sql` and regenerate `migrations.generated.ts`, otherwise `test/migrations.test.ts` fails and Vercel deploys miss the change.
- PGlite is single-connection: `getBrain(s, sql)` takes the request's transaction to avoid waiting on itself; follow that pattern when calling into the DB from inside a handler.
- The repo lives on an NTFS drive (`/media/tenix/New Volume`): every file shows mode 777, `.git/config` has `filemode = false`, `ignorecase = true`, `symlinks = false`, and installs/typechecks are slow. `.gitattributes` forces LF. `git` is not on the shell PATH on this machine.
- The repo scripts resolve the root with `fileURLToPath(new URL('..', import.meta.url))`. They used `.pathname`, which kept `%20` for the space in "New Volume": `embed-migrations` failed and `check:boundaries` scanned nothing yet printed OK. It now fails if a rule finds no files.
- `node_modules` is a Linux install (pnpm store at `/media/tenix/New Volume/dev/caches/pnpm-store/v10`); `esbuild` and `sharp` binaries are linux-x64. If they break, run `pnpm install --frozen-lockfile`.
- The brief rules live in `design.ts` (`readBriefText`, `parsePlotSize`) and `assistant.ts` `respond()` calls them before applying the learned lexicon: change brief parsing in `design.ts`, intent/answers in `assistant.ts`.
